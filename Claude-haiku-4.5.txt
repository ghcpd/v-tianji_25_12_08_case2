### **Issue #1: API Version Mismatch in Analytics Service**
- **Issue Type:** Outdated Endpoint (Version Inconsistency)
- **Location:** api.ts, line 108
- **API Endpoint:** `/api/v2/analytics/metrics`
- **Problem Description:** The `getMetrics` endpoint uses `/api/v2/` while other analytics endpoint `getTrends` uses `/api/v1/`. This version inconsistency indicates the API service wasn't updated together. The v2 endpoint might return a different data structure than v1.
- **Evidence:** 
  - Line 108: `getMetrics` uses `/api/v2/analytics/metrics`
  - Line 112: `getTrends` uses `/api/v1/analytics/trends`
- **Impact:** API response structures between v1 and v2 differ. If v2 returns data in a different format, the Analytics component will fail to render charts correctly or crash.

### **Issue #2: Schema Mismatch - Activity Data Structure**
- **Issue Type:** Schema Mismatch
- **Location:** api.ts, line 33; Dashboard.tsx, line 66
- **API Endpoint:** `/api/v1/dashboard/activity`
- **Problem Description:** The `Activity` interface expects a `userId: number` field, but Dashboard.tsx never uses this field. The interface structure might not match actual API responses if the API returns `user_id` (snake_case) instead of `userId` (camelCase).
- **Evidence:**
  - Interface definition (api.ts:33-37): Has `userId` field
  - Usage in Dashboard (line 66-68): Only displays `type`, `description`, and `timestamp`
  - No validation of `userId` field
- **Impact:** If API returns snake_case or different structure, TypeScript won't catch it at runtime. JSON parsing might fail or userId could be undefined.

### **Issue #3: Missing Type Safety - AnalyticsData Metrics Array**
- **Issue Type:** Schema Mismatch
- **Location:** api.ts, lines 42-48; Analytics.tsx, lines 82-85
- **API Endpoint:** `/api/v2/analytics/metrics`
- **Problem Description:** The `AnalyticsData.metrics` is typed as an array of objects with `period`, `views`, `clicks`, `conversions`, and `revenue`. However, the Analytics component expects `dataKey="period"` in the LineChart, but the interface doesn't explicitly define that property structure. If the API returns `date` instead of `period`, or uses different field names, charts will fail.
- **Evidence:**
  - Interface (line 42-48): Defines metrics array but doesn't guarantee exact field names
  - Analytics usage (line 82): `<XAxis dataKey="period" />` expects exact field name
  - No validation of metrics structure
- **Impact:** Charts won't render if API returns different field names. Silent data misalignment.

### **Issue #4: Nested Object Type Safety - User Profile**
- **Issue Type:** Schema Mismatch  
- **Location:** api.ts, lines 19-24; Users.tsx, lines 54-60
- **API Endpoint:** `/api/v1/users` and `/api/v1/users/{id}`
- **Problem Description:** The `User.profile` object has hardcoded properties (`avatar`, `department`, `location`), but if the API returns additional fields or uses different field names (e.g., `department_name`), the code won't validate this. Also, avatar URL format isn't validated.
- **Evidence:**
  - Interface (api.ts:20-24): Defines profile with specific fields
  - Usage (Users.tsx:55-59): Accesses `user.profile.avatar`, `user.profile.department`, `user.profile.location` with no validation
- **Impact:** If API response has different field names or missing properties, UI displays undefined/null values or crashes.

### **Issue #5: Outdated Settings Endpoint - Potential v2 Upgrade**

  - Line 123: `updateSettings` uses `/api/v1/settings`
  - Analytics v2 upgrade (line 108) suggests API versioning pattern change
- **Impact:** Requests to outdated endpoint return 404 Not Found errors. Settings page fails to load.
