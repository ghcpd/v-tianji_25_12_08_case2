1) Issue Type: Outdated Endpoint

- API Endpoint (previous): /api/v2/analytics/metrics
- Problem Description: The code used a v2 analytics endpoint while the rest of the app and the live API use v1. This causes 404/ENOTFOUND or incorrect routing in environments that only expose v1.
- Evidence: Inconsistent versioning in src/services/api.ts; analyticsService.getMetrics previously called /api/v2/... while other endpoints are /api/v1/...
- Impact: Analytics requests will fail or route to a different handler; UI will show missing analytics or errors.
- Fix: Aligned to /api/v1/analytics/metrics and added normalizeAnalyticsData to defensively map snake_case/strings to the shape expected by Analytics components.
- Tests: api.spec.ts includes a test that verifies the request is handled with /api/v1/analytics/metrics and response normalization.

2) Issue Type: Schema Mismatch (User shape)
- Location: Service normalization: api.ts — normalizeUser (line 69). Component usages: Users.tsx lines ~56–80 (profile/avatar/status usage).
- API Endpoint(s): /api/v1/users (getUsers/getUserById/createUser/updateUser)
- Problem Description: Components assume each User has profile and createdAt and status uses 'active'|'inactive'. Backend may return:
  - created_at (snake_case) instead of createdAt,
  - profile may be missing/null,
  - status values like 'enabled'/'disabled' or other variants,
  - name under full_name, role under user_role.
  This mismatch can produce runtime errors (accessing profile.avatar on null) or incorrect UI text.
- Evidence: Users.tsx directly uses user.profile.avatar and user.profile.department and expects createdAt and status to exist. Tests in api.spec.ts simulate an API returning created_at, full_name, enabled and missing profile and assert that normalization produces the expected client-friendly User.
- Impact: Unhandled nulls cause runtime view crashes or wrong display; users may see empty data or get unhandled exceptions.
- Fix: Added normalizeUser() mapping:
  - created_at -> createdAt
  - full_name -> name
  - user_role -> role
  - status 'enabled' -> 'active'
  - ensure profile always non-null with safe defaults
  and applied normalization in getUsers, getUserById, createUser, updateUser.
- Tests: Added test to confirm normalization behavior and safe defaults.

3) Issue Type: Schema Mismatch (Dashboard stats / activity / growth)
- Location: Service normalization: api.ts — normalizeActivity (line 112) and normalizeDashboardStats (line 122). Dashboard reads stats in Dashboard.tsx lines ~1–120.
- API Endpoint(s): /api/v1/dashboard/stats, /api/v1/dashboard/activity
- Problem Description: Backend may:
  - return recent_activity (snake_case) rather than recentActivity,
  - return growth as a decimal (0.05) while UI expects percentage (5),
  - activity timestamps and user id fields may be snake_case (created_at, user_id).
- Evidence: Dashboard UI expects stats.growth to display as {stats.growth}%, and the component maps Activity.timestamp via new Date(activity.timestamp).normalizeActivity now handles these variants.
- Impact: Growth could render as 0.05% (wrong display), or activities could miss userId/timestamp leading to blank entries.
- Fix: normalizeDashboardStats coerces growth:
  - if growth <= 1, convert to percent (growth*100),
  - normalize recent_activity -> recentActivity
  - normalize activity fields (action/desc vs type/description; created_at vs timestamp; user_id vs userId)
- Tests: Added test that supplies snake_case recent_activity and growth_rate = 0.05 and asserts growth -> 5 and activity normalization.
