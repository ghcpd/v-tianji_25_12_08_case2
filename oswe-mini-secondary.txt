## 📌 Issue 2 — Schema mismatch: conversionRate units & user fields normalization

- Issue Type: Schema Mismatch (two separate sub-issues)
  - A) Analytics conversionRate unit inconsistency
  - B) User schema field naming & optional/multiple shapes

### A) Analytics conversionRate normalization
- Location: api.ts (getMetrics; originally returning response.data unchanged)
- API Endpoint: /api/v2/analytics/metrics
- Problem Description: The application assumed `summary.conversionRate` is a fraction 0–1 (code multiplies it by 100 when displaying). But many APIs return conversion rates as percentages (0–100). If API returned 5 for 5%, the UI would show 500% (wrong).
- Evidence: Analytics component multiplies conversionRate by 100 when rendering (calls (conversionRate * 100).toFixed(2)). To be robust, service should normalize various units.
- Impact: Wrong conversion rate display (e.g., 5% shown as 500% or vice versa), bad UX and incorrect business insights.
- Fix implemented: `getMetrics` now normalizes `data.summary.conversionRate` — if value > 1 (e.g., 5), it divides by 100 so it becomes a proper fraction (0.05).

Tests added:
- analytics.spec.ts
  - test ensures conversionRate >1 gets normalized to fraction (5 → 0.05)
  - test ensures already fractional values (0.03) are preserved

### B) User schema normalization (snake_case vs camelCase, booleans and missing profile)
- Location: api.ts (userService.getUsers / getUserById; previously returned response.data unchanged)
- API Endpoint(s): /api/v1/users and /api/v1/users/:id
- Problem Description: Backend APIs often use snake_case (created_at) or different shape for profile fields, and "status" may be inconsistent (e.g., boolean enabled, or string values like 'enabled', 'disabled', 'active'). The frontend code expects camelCase `createdAt`, nested profile fields, and status equal to 'active'/'inactive'. Without normalization, UI may crash or display incorrect values.
- Evidence: `Users` component expects `createdAt` and `profile.avatar` etc. The service returned raw API payloads; if the API used `created_at` or `enabled` flags the UI could break.
- Impact: Missing or incorrectly shaped fields could cause UI rendering errors, runtime exceptions (undefined access) or inaccurate status displays.
- Fix implemented: Added a helper `normalizeUser(raw: any): User` which:
  - maps `created_at` → `createdAt`
  - handles `status` (strings like 'enabled' or boolean `enabled`) to canonical 'active'/'inactive'
  - normalizes `profile` fields from `avatar_url`, `dept`, `city` or missing profile
  - ensures getUsers handles both array responses and wrapped responses ({ users: [...] })

Files changed:
- api.ts — added export of apiClient, added normalizeUser helper, updated userService.getUsers and getUserById to return normalized objects.

Tests added:

  - tests: GET /users returns created_at and avatar_url/dept/city → normalized on getUsers
  - tests: getUserById handles singular object with created_at, enabled boolean and avatar → normalized
