2) Issue Type: Schema Mismatch — Optional Profile + status typing
- Location: api.ts User interface and Users.tsx lines ~1–120
- API Endpoint: `/api/v1/users`, `/api/v1/users/:id`
- Problem Description: `User.profile` and properties inside were declared required in TypeScript. In practice many APIs omit nested profile data from list endpoints or for users with incomplete profiles. The UI used direct `user.profile.avatar` and `selectedUser.profile.department` access which would throw if `profile` is undefined. Also `status` was typed as `'active' | 'inactive'` but APIs sometimes return other values like `'pending'`, `'suspended'`, or use booleans.
- Evidence: `userService.getUsers()` returns arrays from `/api/v1/users`. The `Users` component uses `user.profile.avatar` without guarding. The defined `User` type required `profile`. This mismatch (API may omit profile) can cause runtime TypeError.
- Impact: Clicking user cards or rendering avatars could throw `Cannot read properties of undefined` and break the Users page. Also narrow `status` union can cause false type assumptions.
- Fix applied:
  - In api.ts:
    - Made `profile` optional (`profile?: { avatar?: string; department?: string; location?: string }`).
    - Changed `status` to a plain `string` to accept additional server values.
  - In Users.tsx:
    - Guarded avatar rendering with `user.profile && user.profile.avatar`.
    - Rendered profile details only if `selectedUser.profile` exists; used fallback placeholders for missing values.
  - Added unit tests:
    - `getUserById handles missing profile` to ensure service returns user without profile and UI code won't crash (service-level).
    - `getUsers returns array of users` to check shape for a user with profile present.
- Files changed: api.ts, Users.tsx, test: api.test.ts
